# GAEO Health Check: 전체 건강검진 절차

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| 사이트 전반을 한 번에 훑는다 | 앞으로 **뭘 만들지** → `/gaeo-strategy` |
| 정기 건강검진 | 특정 증상 하나 → `/gaeo-bug` |
| 어디가 약한지 모르는 상태 | 방금 변경분 검수 → `/gaeo-review` |

`/gaeo-strategy`와의 경계: **Health는 "지금 어디가 아픈가"(현재 상태), Strategy는 "앞으로 뭘 할까"(미래 방향).**

⚠️ `/verify`는 현재 Claude Code 버전에 없다. 있다고 가정하고 호출하지 않는다.
대신 저장소의 `test_*.py`/`test_*.js`와 bundled `code-review`·`security-review`를 쓴다.

## 0단계: 기계 점검부터 (AI 0명)

```
python3 ops_status.py --deep          # 시세·자동분석·관측 종목·지표 출처·공시·모의투자·Evolution·예정 시험 (LLM 0)
python3 gaeo_check.py quick           # 핵심 계약 검사
```
그리고 `docs/operations/STATUS.md`의 "남은 위험"과 `docs/operations/repair_requests/`(있으면)를 읽는다.
여기서 장애·확인 불가가 0이고 사용자가 특정 영역을 지목하지 않았으면 **점검 요청은 여기서 끝낸다**(정상 서버를 바꾸지 않는다).

## Agent 구성 (2026-09-10 절약형)

기본 0명. 위 기계 점검이 이상을 보이거나 사용자가 영역을 지목했을 때만 **그 영역의 검토자 1명**을 부른다(동시 2명 이내).

- 코드·성능·기술부채: 메인 작업자가 직접 본다(`gaeo-engineer`를 따로 부르지 않는다)
- 버그·회귀·렌더링 이상: `gaeo-qa`
- 보안·API·데이터 노출 의심: `gaeo-security`
- UX·디자인 일관성 요청: `gaeo-ux-designer`

**상황별 추가(순서대로, 동시 아님)**:
- 최근 분석 로직 변경이 있었으면 `gaeo-quant-research`
- 최근 콘텐츠·SEO 변경이 많았으면 `gaeo-growth-lead`
- 성과 검증이 오래 안 됐으면 `gaeo-data-analyst`

## 절차

1. 각 Agent가 자기 담당 영역을 병렬로 점검한다(코드/성능/기술부채, 버그/회귀, 보안, UX, 필요시 분석력/SEO).
2. 발견 사항을 모아서 다음 네 등급으로 분류한다.
   - **지금 즉시 고쳐야 하는 것**: 실제 장애·보안 위험·데이터 오류처럼 방치하면 안 되는 문제
   - **다음 개발에서 처리하면 되는 것**: 문제이긴 하지만 급하지 않은 것
   - **나중에 해도 되는 것**: 개선하면 좋지만 우선순위가 낮은 것
   - **굳이 건드릴 필요 없는 것**: 검토했지만 문제 없다고 확인된 것(오탐 방지용으로 명시)
3. 진단 결과를 보고한다.

## ⭐ 원칙

- **기본은 READ ONLY다.** 점검하면서 사소한 것(오탈자 등)이라도 대표 요청 없이 임의로 고치지 않는다. 발견하고 보고만 한다.
- "지금 즉시 고쳐야 하는 것"으로 분류한 항목이라도, 대표가 수정을 요청하기 전에는 실행하지 않는다. 다만 그게 실제 서비스 장애 수준(예: 사이트가 안 뜬다, 결제/계좌 정보가 새고 있다)이면 즉시 발견 사실을 먼저 알리고 지시를 기다린다.
- 진단 결과 중 코드 수정이 필요한 항목은 `/gaeo-build` 또는 `/gaeo-bug`로 이어가도록 안내한다.

## 이 스킬이 자동으로 제안되는 상황(주간 Health Recommendation)

매주 금요일 오전 9시(Asia/Seoul), 최근 한 주 코드 변경량이 클 때 `/gaeo-health`를 대표에게 **제안**한다(자동 실행 아님). 변경이 거의 없으면 억지로 권하지 않는다.

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까 (2026-09-10 절약형으로 개정)

기본은 **메인 작업자 1명**이다. 정상 서버 점검에는 AI를 0명 쓴다(`python3 ops_status.py`·`python3 gaeo_check.py`가 한다).
Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 | 사람 수 |
|---|---|
| 정상 점검·요약·예정 시험 | 0명 (일반 프로그램) |
| 작은 작업(문구·한 줄 수정·단일 화면·소규모 버그) | 메인 1명 + 기계 검사 |
| 보통 작업(기능 구현·다중 파일) | 메인 1명, 독립 판단이 필요한 대목에만 검토자 1명 |
| 보안·장부·투자 성적 의미·배포 경계를 바꾸는 변경 | 메인 1명 + 분리된 검토자 1명(관점별로 **순서대로**, 동시에 여럿 부르지 않는다) |

**동시 실행은 총 2명 이내.** 수정하는 작업자는 언제나 하나이고 검토자는 findings와 근거만 돌려준다(같은 파일을 동시에 고치지 않는다).
자식 Agent의 재귀 생성·끝없는 회의·같은 원본 반복 읽기 금지. 일이 끝난 Agent는 종료한다.
같은 모델의 다른 역할은 완전히 독립된 보증이 아니다 — 기계 검사(`test_*`)를 대체하지 않는다.
역할 파일의 "읽기 전용"은 지침이다(Bash가 있으면 기술적으로 쓸 수 있다). 물리적 차단이라고 말하지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서 (공통 기준 — `docs/HARNESS.md` §3)

`Build` → 기계 검사(`python3 gaeo_check.py quick`/`premerge`) → (중요한 변경만) 독립 검토 → Commit/Push → PR → CI → 병합.
검사·검토에서 FAIL이면 배포하지 않는다. 자동 commit/push 플러그인을 쓰지 않는다.
PR 생성·main 병합은 **그 세션의 사용자 지시 범위 안**에서 확인 없이 진행한다(2026-08-01 고정 승인). 이 순서는 품질 절차이지
추가 승인 단계가 아니다. 단 파괴적·되돌리기 어려운 것(force push·이력 재작성·원장·산식·사전등록 상수 변경·유료 전환)은 항상 명시 승인.
과거 세션의 넓은 승인을 영구 배포 권한으로 쓰지 않는다.
