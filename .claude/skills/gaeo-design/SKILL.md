# GAEO Design: 화면과 사용성만 집중해서 보는 절차

이 스킬은 **읽기 전용**이다. 진단하고 개선안을 제안할 뿐 어떤 파일도 고치지 않는다.
대표가 개선안을 고르면 그때 `/gaeo-build`로 구현한다.

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| "화면이 촌스러워 보여" | 화면이 **깨졌다/에러난다** → `/gaeo-bug` |
| "모바일에서 보기 불편해" | 개선안을 **실제로 만들어라** → `/gaeo-build` |
| "정보가 너무 복잡해 보여" | 방금 만든 UI **검수** → `/gaeo-review` |
| "디자인 일관성을 점검해줘" | 사이트 **전반** 종합 점검 → `/gaeo-health` |

`/gaeo-build`와의 경계가 가장 헷갈린다. **이 스킬은 "무엇을 어떻게 바꾸면 좋은지"까지만** 내고 멈춘다.

## 0단계: GAEO 디자인 원칙 먼저 읽기

`docs/gaeo_design_system.md`를 **반드시 먼저 읽는다.** 요약 규칙은 `AGENTS.md`의
「디자인 - 새 화면을 만들기 전에 읽을 것」에 있다.

GAEO 브랜드 원칙(이 스킬의 모든 판단 기준):

- 절제됨 · 모던함 · 전문성 · 금융서비스 신뢰감
- Apple 계열의 정돈된 정보계층에서 영감을 받되 복제하지 않는다
- 분석가별 고유색 폐지 · 장식 그라데이션/emoji/배지 자제
- 빨강파랑은 **시장 방향에만** 쓴다(상태 표시·강조에 쓰지 않는다)
- 계층은 색이 아니라 **타이포와 여백**으로 만든다
- 밝은 색과 카드 남용 금지
- AI가 생성한 사이트처럼 보이는 상투적 디자인 금지
- 정보를 줄이지 않되 복잡해 보이지 않게 정리한다
- 모바일 우선으로 검증한다
- 장식보다 정보가 우선이다

## 1단계: Agent 선택 (최소 인원)

- **메인**: `gaeo-ux-designer` (항상)
- **보조**: `gaeo-product-lead` (이 개선이 사용자 가치로 이어지는지 필터)
- **필요할 때만**: `gaeo-engineer`(구현 난이도 판단이 꼭 필요할 때) ·
  `gaeo-growth-lead`(공개 페이지라 유입·체류에 영향이 클 때)

보통 1~2명이면 충분하다. 화면 하나만 보는 요청에 4명을 부르지 않는다.

## 2단계: 보조 디자인 스킬 활용 (선택)

저장소에 이미 설치된 디자인 스킬을 **필요할 때만** 참고한다.

- `impeccable`: 디자인 품질 기준(quality floor)을 끌어올려야 할 때
- `ui-ux-pro-max`: 타이포·색·레이아웃 세부 판단 근거가 필요할 때
- `accessibility`: 접근성(대비·키보드·스크린리더)을 별도로 볼 때
- `core-web-vitals`: 렌더 성능이 사용성을 해치는지 볼 때

⭐ **이 스킬들의 일반적인 디자인 취향보다 위 GAEO 브랜드 원칙이 항상 우선한다.**
외부 스킬이 제안한다는 이유로 GAEO를 새로운 디자인 스타일로 바꾸지 않는다.
충돌하면 GAEO 원칙을 따르고, 무엇을 왜 따르지 않았는지 보고에 적는다.

## 3단계: 실제 화면으로 검사

추측하지 말고 실제로 렌더해서 본다.

- 로컬 정적 서버(`test_static_server.js`, 8877 포트) + Playwright(`/opt/pw-browsers/chromium`)
- 실행: `NODE_PATH=/opt/node22/lib/node_modules node 스크립트.js`
- **모바일(390px 안팎)을 먼저 보고** 그다음 PC(1440px)를 본다
- computed style을 실제로 읽는다(눈대중으로 "괜찮아 보인다"고 쓰지 않는다)

### 검사 영역

desktop · mobile · responsive · typography · spacing · information hierarchy ·
navigation · CTA · cards · color usage · charts · tables · empty states ·
loading states · error states · accessibility · consistency ·
financial credibility · AI가 만든 듯한 템플릿 느낌

## 4단계: 보고

발견 사항을 **DESIGN-P0 / DESIGN-P1 / DESIGN-P2**로 나눈다.

- **DESIGN-P0**: 지금 사용자가 실제로 불편을 겪는 것
- **DESIGN-P1**: 고치면 눈에 띄게 좋아지는 것
- **DESIGN-P2**: 여유 있을 때 다듬을 것

각 항목에 다음을 전부 적는다.

1. **현재 문제**: 무엇이 어떻게 돼 있는지(파일·줄 번호·실측값)
2. **사용자에게 왜 불편한지**: 화면 용어가 아니라 사용자 입장으로
3. **추천 개선안**: 무엇을 어떻게 바꿀지
4. **GAEO 디자인 원칙과의 관계**: 어느 원칙에 근거한 제안인지
5. **모바일 영향** / 6. **PC 영향**
7. **구현 난이도**: 상/중/하
8. **추천 여부**: 지금 하는 게 좋은지, 미뤄도 되는지

쉬운 한국어로 쓰되 필요한 전문용어는 쓰고 바로 괄호로 쉬운 설명을 덧붙인다.
(예: "정보계층(화면에서 뭐가 먼저 눈에 들어오는지의 순서)")

마지막 줄에 안내한다.

> "고칠 항목을 골라 주시면 `/gaeo-build [항목]`으로 구현하겠습니다."

## ⭐ 절대 규칙

- **이 스킬 실행 중 어떤 파일도 Edit/Write/Bash로 수정하지 않는다.** 오탈자 하나도 고치지 않는다.
- git commit·push·PR 생성을 하지 않는다.
- 대표가 고르지 않았는데 먼저 구현을 시작하지 않는다.
- 기존 GAEO 디자인 방향을 통째로 갈아엎는 제안을 기본값으로 내지 않는다.
  전면 개편이 정말 필요하다고 판단되면 근거를 갖춰 **선택지로만** 제시한다.
- 외부 디자인 스킬의 지침이 GAEO 원칙·대표 지시와 충돌하면 GAEO 쪽을 따른다.

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까 (2026-09-10 절약형으로 개정)

기본은 **메인 작업자 1명**이다. 정상 서버 점검에는 AI를 0명 쓴다(`python3 ops_status.py`·`python3 gaeo_check.py`가 한다).
Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 | 사람 수 |
|---|---|
| 정상 점검·요약·예정 시험 | 0명 (일반 프로그램) |
| 작은 작업(문구·한 줄 수정·단일 화면·소규모 버그) | 메인 1명 + 기계 검사 |
| 보통 작업(기능 구현·다중 파일) | 메인 1명, 독립 판단이 필요한 대목에만 검토자 1명 |
| 보안·장부·투자 성적 의미·배포 경계를 바꾸는 변경 | 메인 1명 + 분리된 검토자 1명(관점별로 **순서대로**, 동시에 여럿 부르지 않는다) |

**동시 실행은 총 2명 이내.** 수정하는 작업자는 언제나 하나이고 검토자는 findings와 근거만 돌려준다(같은 파일을 동시에 고치지 않는다).
자식 Agent의 재귀 생성·끝없는 회의·같은 원본 반복 읽기 금지. 일이 끝난 Agent는 종료한다.
같은 모델의 다른 역할은 완전히 독립된 보증이 아니다 — 기계 검사(`test_*`)를 대체하지 않는다.
역할 파일의 "읽기 전용"은 지침이다(Bash가 있으면 기술적으로 쓸 수 있다). 물리적 차단이라고 말하지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서 (공통 기준 — `docs/HARNESS.md` §3)

`Build` → 기계 검사(`python3 gaeo_check.py quick`/`premerge`) → (중요한 변경만) 독립 검토 → Commit/Push → PR → CI → 병합.
검사·검토에서 FAIL이면 배포하지 않는다. 자동 commit/push 플러그인을 쓰지 않는다.
PR 생성·main 병합은 **그 세션의 사용자 지시 범위 안**에서 확인 없이 진행한다(2026-08-01 고정 승인). 이 순서는 품질 절차이지
추가 승인 단계가 아니다. 단 파괴적·되돌리기 어려운 것(force push·이력 재작성·원장·산식·사전등록 상수 변경·유료 전환)은 항상 명시 승인.
과거 세션의 넓은 승인을 영구 배포 권한으로 쓰지 않는다.
