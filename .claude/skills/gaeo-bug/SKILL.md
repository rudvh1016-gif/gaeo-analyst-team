# GAEO Bug: 문제를 찾아 고치는 절차

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| 원인 모를 증상·오류가 보고됨 | 방금 **내가 바꾼 것** 검수 → `/gaeo-review` |
| "이거 왜 이래 / 화면이 깨졌어" | 고장은 아닌데 **보기 불편** → `/gaeo-design` |
| 예전엔 됐는데 지금 안 된다 | 전반을 **훑어보고** 싶다 → `/gaeo-health` |

`/gaeo-review`와의 경계: **Bug는 "원인을 모르는 증상"에서 출발한다.** 변경분 검수는 Review다.

⚠️ `/debug`는 현재 Claude Code 버전에 없다. 있다고 가정하고 호출하지 않는다.

**추측만으로 코드를 수정하지 않는다.** 증상을 먼저 재현하고, 진짜 원인을 확인한 다음 고친다.

## 0단계: 이미 알려진 사고인지

`docs/operations/STATUS.md`의 "확정된 사실·남은 위험", `python3 ops_status.py --deep` 출력, `docs/operations/repair_requests/`(있으면)를 먼저 읽는다.
같은 서명(INC 번호)의 사고면 거기 적힌 확인 순서부터 따른다. 새로 조사하지 않는다.

## Agent 구성 (2026-09-10 절약형)

기본은 메인 작업자 1명이다(재현 → 원인 → 최소 수정 → 기계 검사). 아래 조건에 해당하면 **1명만** 추가한다(동시 2명 이내).
- 재현 자체가 어려운 화면·시간대·상호작용 문제면 `gaeo-qa`

- 금융 계산·점수·판단 결과가 이상하면 `gaeo-quant-research` 추가
- 계정·인증·데이터 노출과 관련된 증상이면 `gaeo-security` 추가
- "예전엔 맞았는데 최근에 이상해졌다"처럼 과거 데이터와 비교가 필요하면 `gaeo-data-analyst` 추가

## 절차

1. **문제 재현**: 보고된 증상을 실제로 재현한다. 재현이 안 되면 "재현 안 됨"이라고 그대로 보고하고, 재현 조건(브라우저, 화면 크기, 시각, 데이터 상태 등)을 더 구체적으로 물어본다.
2. **증거 확인**: 에러 메시지, 콘솔 로그(`pageerror`), 스크린샷, 관련 데이터 파일의 실제 값을 확인한다.
3. **근본 원인 분석**: 보이는 증상이 아니라 오류가 발생한 진짜 이유를 찾는다. 이 저장소는 스코프를 벗어난 파일 수정, 캐시 무효화 누락, 타임존/휴장일 처리 실수 같은 패턴으로 실제 사고가 반복된 이력이 있다(`AGENTS.md` 참고). 비슷한 패턴인지 먼저 의심한다.
4. **영향범위 확인**: 이 버그가 다른 화면·데이터에도 같은 원인으로 영향을 주고 있는지 확인한다.
5. **최소 수정**: 원인에 해당하는 부분만 고친다. 김에 다른 것도 고치지 않는다.
6. **회귀 테스트**: 관련 `test_*.py`/`test_*.js`를 돌려 이 수정이 다른 걸 깨지 않았는지 확인한다.
7. **재검증**: 원래 증상이 재현됐던 조건으로 다시 확인해 실제로 사라졌는지 본다.

## ⭐ 하지 말 것

- **추측만으로 수정하지 않는다.** "아마 이게 문제일 것 같다"는 감으로 코드를 고치지 않는다. 먼저 확인한다.
- **증상만 가리는 임시 수정을 피한다.** 예: 에러가 안 보이게 try/catch로 감싸기만 하고 진짜 원인을 안 고치는 식.
- 버그와 무관한 리팩터링을 같이 하지 않는다.

## 보고 형식

- **증상**: 무엇이 어떻게 이상했는지
- **재현 조건**: 어떻게 하면 재현되는지
- **근본 원인**: 왜 이런 일이 벌어졌는지
- **수정 내용**: 무엇을 어떻게 고쳤는지(최소 범위)
- **재검증 결과**: 원래 증상이 사라졌는지, 회귀 테스트는 통과했는지

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까 (2026-09-10 절약형으로 개정)

기본은 **메인 작업자 1명**이다. 정상 서버 점검에는 AI를 0명 쓴다(`python3 ops_status.py`·`python3 gaeo_check.py`가 한다).
Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 | 사람 수 |
|---|---|
| 정상 점검·요약·예정 시험 | 0명 (일반 프로그램) |
| 작은 작업(문구·한 줄 수정·단일 화면·소규모 버그) | 메인 1명 + 기계 검사 |
| 보통 작업(기능 구현·다중 파일) | 메인 1명, 독립 판단이 필요한 대목에만 검토자 1명 |
| 보안·장부·투자 성적 의미·배포 경계를 바꾸는 변경 | 메인 1명 + 분리된 검토자 1명(관점별로 **순서대로**, 동시에 여럿 부르지 않는다) |

**동시 실행은 총 2명 이내.** 수정하는 작업자는 언제나 하나이고 검토자는 findings와 근거만 돌려준다(같은 파일을 동시에 고치지 않는다).
자식 Agent의 재귀 생성·끝없는 회의·같은 원본 반복 읽기 금지. 일이 끝난 Agent는 종료한다.
같은 모델의 다른 역할은 완전히 독립된 보증이 아니다 — 기계 검사(`test_*`)를 대체하지 않는다.
역할 파일의 "읽기 전용"은 지침이다(Bash가 있으면 기술적으로 쓸 수 있다). 물리적 차단이라고 말하지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서 (공통 기준 — `docs/HARNESS.md` §3)

`Build` → 기계 검사(`python3 gaeo_check.py quick`/`premerge`) → (중요한 변경만) 독립 검토 → Commit/Push → PR → CI → 병합.
검사·검토에서 FAIL이면 배포하지 않는다. 자동 commit/push 플러그인을 쓰지 않는다.
PR 생성·main 병합은 **그 세션의 사용자 지시 범위 안**에서 확인 없이 진행한다(2026-08-01 고정 승인). 이 순서는 품질 절차이지
추가 승인 단계가 아니다. 단 파괴적·되돌리기 어려운 것(force push·이력 재작성·원장·산식·사전등록 상수 변경·유료 전환)은 항상 명시 승인.
과거 세션의 넓은 승인을 영구 배포 권한으로 쓰지 않는다.
