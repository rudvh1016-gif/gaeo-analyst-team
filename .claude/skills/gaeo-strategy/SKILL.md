# GAEO Strategy: 다음에 뭘 해야 하는지 정하는 절차

이 스킬은 **읽기 전용**이다. 저장소 상태를 읽고 조사해서 우선순위 제안을 만들 뿐, 어떤 파일도 고치지 않는다. 코드 변경은 대표가 항목을 선택해 `/gaeo-build`를 실행할 때만 시작된다.

## 0단계: 현재 상태 파악

1. 저장소 루트 `AGENTS.md`·`CLAUDE.md`·`docs/CURRENT_STATUS.md`(있으면)를 읽어 최근 작업 이력과 현재 상태를 파악한다.
2. `git log --oneline -30`으로 최근 변경 흐름을 훑는다.
3. 지난 Strategy 실행 이후 무엇이 바뀌었는지 감을 잡는다(정밀분석 갱신 빈도, UI 변경, 데이터 파이프라인 사고 이력 등).

## 1단계: 관점별 조사 (병렬 Agent)

**Agent Team 방식을 쓴다.** 여러 전문분야가 동시에 독립적으로 조사하고 의견을 비교해야 하는 전형적인 경우이기 때문이다. 각 Agent는 서로 다른 관점에서 **독립적으로** 조사하게 하고, 서로의 결론을 미리 알려주지 않는다(편향 방지).

Agent 도구로 아래를 **동시에(같은 메시지에서 병렬로)** 호출한다. 매번 8개를 전부 부르지 않는다. 아래 기본 조합에서 시작하고, 이번 회차에 특별히 봐야 할 이유가 있을 때만 나머지를 추가한다.

**기본 조합(대부분의 회차)**:
- `gaeo-product-lead`(subagent_type): 뒤에서 다른 결과들을 종합할 역할이므로, 1단계에서는 "현재 뭐가 부족해 보이는지" 자신의 1차 시각만 짧게 받아둔다.
- `gaeo-quant-research`: 분석 로직·GAEO Score·투자 판단 품질 관점에서 개선 여지 조사
- `gaeo-ux-designer`: PC/모바일 사용성·정보 구조·디자인 일관성 관점에서 개선 여지 조사
- `gaeo-growth-lead`: 유입·재방문·SEO·광고수익 관점에서 개선 여지 조사

**필요할 때만 추가**:
- `gaeo-data-analyst`: 최근 산식 변경이 있었거나, "정말 좋아졌는지" 실증 확인이 우선순위 판단에 필요할 때
- `gaeo-engineer`: 순수 기술부채·인프라 문제가 의심될 때(성능, 코드 구조 등)

각 Agent에게 주는 프롬프트에는 반드시 다음 두 질문을 포함시킨다.

> "이 제안이 GAEO의 투자 판단 품질을 높이는가?"
> "이 제안이 사용자 증가·만족·재방문·성장에 기여하는가?"

그리고 저장소 경로와 함께 "지금 저장소를 읽고, 개선하면 좋을 것 같은 항목을 3~5개 찾아서 위 두 질문에 답해달라"고 명확히 지시한다.

## 2단계: 종합

`gaeo-product-lead` Agent를 한 번 더 호출하되, 이번에는 1단계에서 나온 모든 결과를 프롬프트에 그대로 넣어 **종합**을 요청한다.

- 두 질문 모두 약한 항목은 우선순위를 낮춘다(완전히 버리지는 않는다. P2로 내린다).
- 서로 충돌하는 제안이 있으면 조정 근거를 명시한다.
- 이미 gaeo-data-analyst의 실측 근거가 있는 항목은 그 근거를 우선한다.

## 3단계: 보고

최종 결과를 P0(지금 바로) / P1(다음 순서) / P2(여유 있을 때)로 나눠 보고한다. 각 항목에:

- 무엇인지 · 왜 필요한지
- 사용자 가치 · 분석 품질 영향 · 사용자 성장 영향
- 개발 난이도(상/중/하) · 위험도(상/중/하)
- 추천 이유

쉬운 한국어로 쓰되, 필요한 전문용어는 쓰고 바로 괄호로 쉬운 설명을 덧붙인다.

마지막 줄에 다음을 안내한다.

> "진행할 항목을 골라 말씀해 주시면 `/gaeo-build [항목]`으로 바로 시작할 수 있어요."

## ⭐ 절대 규칙

- **이 스킬 실행 중 어떤 파일도 Edit/Write/Bash로 수정하지 않는다.** 코드를 고치고 싶은 유혹이 들어도 참는다. 그건 Build의 몫이다.
- git commit·push·PR 생성을 하지 않는다.
- 대표가 아직 항목을 고르지 않았는데 먼저 구현을 시작하지 않는다.
