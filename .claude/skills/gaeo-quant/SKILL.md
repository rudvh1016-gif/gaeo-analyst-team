# GAEO Quant: 분석력을 실제로 검증하는 절차

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| "이 산식이 정말 나아졌나" 검증 | 일반적인 개발 방향 → `/gaeo-strategy` |
| 적중률·백테스트·성과 비교 | 단순 코드 수정 → `/gaeo-build` |
| GAEO Score 변경의 실제 효과 확인 | 화면 표시 문제 → `/gaeo-design` |

⚠️ **일반 개발·전략 질문에 이 스킬이 끌려 나오면 안 된다.** 분석 산식 자체의 성능을 실제
과거 데이터로 검증할 때만 쓴다. 주식·투자라는 단어가 나왔다는 이유만으로 발동하지 않는다.

이 스킬의 핵심은 **"새 지표를 추가하는 것"이 아니라 "실제 과거 결과로 분석력이 좋아졌는지 검증하는 것"**이다.

## Agent 구성

- `gaeo-quant-research`: 로직 설계·가설 제시
- `gaeo-data-analyst`: 과거 데이터로 실제 검증
- 산식 변경이 확정되면 `gaeo-engineer` 추가(구현)

## 절차

1. **현재 방식 파악**: `gaeo-quant-research`가 `analysis.js`·`analyze_auto.py` 등 현재 점수 산식과 가중치를 읽고 정리한다.
2. **문제/가설 제시**: 어떤 지표가 약한지, 무엇을 바꾸면 나아질 것 같은지 근거와 함께 제시한다. 이 시점에는 아직 "가설"이다.
3. **실증 검증**: `gaeo-data-analyst`가 `history.js`·`analysis_archive.js`·`market_history.js` 등 실제 과거 기록으로 다음을 계산한다.
   - 현재 방식의 적중률/성과(기간별로 나눠서)
   - 변경안을 과거 데이터에 적용했을 때의 성과(가능한 경우)
   - 표본 수, 비교 기준의 공정성
4. **결론**: 변경이 실제로 더 나은 결과를 냈는지, 아니면 표본이 작아 확신하기 어려운지 명확히 구분한다.
5. **구현 여부 결정**: 실증으로 뒷받침되면 `gaeo-engineer`에게 구현을 넘긴다(사실상 `/gaeo-build`로 이어짐). 뒷받침되지 않으면 "지금은 반영하지 않는다"고 명확히 결론짓는다. 근거 없이 "일단 넣어보자"로 넘어가지 않는다.

## ⭐ 원칙

- **분석력이 좋아졌다는 주장에는 가능한 경우 데이터 근거가 있어야 한다.** "이론적으로 맞다"만으로는 부족하다.
- 표본이 적으면(예: 특정 조건 5건 미만) 그렇다고 명시하고 과신하지 않는다.
- 유리한 구간만 보여주는 체리피킹을 하지 않는다. 전체 기간과 비교 구간을 함께 제시한다.
- 개별 종목의 정밀분석(analysis.js 종목 블록)을 이 스킬에서 직접 고치지 않는다. 이건 산식·로직 자체를 다루는 스킬이고, 실제 종목 재분석은 `.claude/skills/종목분석 스킬`의 역할이다.

## 이 스킬이 자동으로 제안되는 상황

`/gaeo-strategy`, `/gaeo-health`, 또는 `/gaeo-build` 도중 아래 조건을 발견하면 사용자에게 이 스킬 실행을 제안한다(자동 실행은 하지 않는다).

- GAEO Score 계산이 바뀌는 작업
- 새로운 투자 지표 추가
- 분석 로직 변경
- 적중률을 오래 검증하지 않은 상태
- 포트폴리오/성적표 관련 계산 로직 변경

제안 문구 예: "이번 변경은 GAEO Score에 영향을 주므로 `/gaeo-quant` 성과 검증을 추천해요."

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까

Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 의미 없이 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 크기 | Agent 수 |
|---|---|
| 작은 작업(오탈자·한 줄 수정·단일 화면 확인) | 1~2명 (또는 메인 세션이 직접) |
| 보통 작업 | 2~4명 |
| 전략 수립·고위험 감사 | 3~5명 |

**8명 전체 동시 호출은 명확한 필요성이 없는 한 금지한다.** 일이 끝난 Agent를 계속 붙들고 있지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서

`Build` → `Review` → **PASS** → Commit/Push. Review에서 FAIL이면 배포하지 않는다.
자동 commit/push 플러그인을 쓰지 않는다.
