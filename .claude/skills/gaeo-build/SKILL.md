# GAEO Build: 정한 것을 실제로 만드는 절차

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| 만들기로 정한 것을 코드로 옮긴다 | 무엇을 만들지 **아직 안 정했다** → `/gaeo-strategy` |
| 대표가 바로 지시한 기능·수정 | 디자인 개선안만 **받아보고 싶다** → `/gaeo-design` |
| | 고장난 것을 **고친다** → `/gaeo-bug` |

`/gaeo-design`과의 경계: **Design은 제안까지, Build는 구현부터.**

## 0단계: 범위 확정

시작 전에 "무엇을 만드는지"를 한 문장으로 요약해서 스스로 확인한다. 대표의 요청이 모호하면(예: "포트폴리오 화면 좀 손봐줘") 범위를 넓게 잡지 말고, 먼저 구체적으로 무엇을 바꾸는지 되물어 확인한 뒤 시작한다.

## 1단계: Agent 선택 (업무 성격에 따라 최소 인원)

`gaeo-engineer`는 항상 포함한다(실제 구현 담당). 여기에 업무 성격에 따라 아래에서 필요한 만큼만 추가한다. 이유 없이 전체를 부르지 않는다.

| 업무 성격 | 추가로 부를 Agent |
|---|---|
| 금융 계산·GAEO Score·분석 산식 관련 | `gaeo-quant-research` (+ 실측 검증이 필요하면 `gaeo-data-analyst`) |
| 화면·디자인 관련 | `gaeo-ux-designer` |
| SEO·콘텐츠 구조·유입 관련 | `gaeo-growth-lead` |
| 계좌·인증·개인정보 관련 | `gaeo-security` |
| 그 외 순수 백엔드/데이터 파이프라인 | Engineer 단독으로 충분한 경우가 많다 |

**마지막 회귀 확인은 기계 검사로 한다**(`python3 gaeo_check.py quick` 또는 관련 묶음, 화면이면 Playwright smoke). `gaeo-qa`는 사람 눈이 필요한 화면·상호작용 문제나 여러 파일에 걸친 구현일 때만 1명 부른다(동시 2명 이내).

간단한 작업(오탈자 수정, 한 줄짜리 버그 수정 등)은 Agent Team을 꾸리지 않고 메인 세션이 직접 처리해도 된다. Agent 수가 많다고 품질이 좋아지는 게 아니다.

## 2단계: 순서

1. **설계**: 무엇을, 어느 파일에, 어떻게 바꿀지 짧게 계획한다.
2. **영향범위 확인**: 이 변경이 건드리는 다른 파일·기능이 있는지 `grep`·`git log`로 미리 확인한다. 특히 `analysis.js`(정밀분석 종목 블록 vs market 블록), `data.js`(기준가 무결성) 같은 스코프가 엄격한 파일은 AGENTS.md의 관련 절을 반드시 다시 읽는다.
3. **구현**: `gaeo-engineer`가 실제 코드를 작성/수정한다. 필요한 전문 Agent(퀀트·UX·Growth·Security)는 구현 전이나 구현 중에 방향을 제시하되, 코드 수정 자체는 Engineer가 한다(여러 Agent가 동시에 같은 파일을 고치면 충돌한다).
4. **테스트**: 관련 `test_*.py`/`test_*.js`를 실행한다. 새 기능이면 필요한 테스트를 새로 만든다.
5. **기본 QA**: `gaeo-qa`로 PC/모바일 렌더링과 회귀 여부를 확인한다.

## ⭐ 금지 사항

- **요청하지 않은 기능 추가 금지.** "이왕 하는 김에" 식으로 범위를 넓히지 않는다.
- **불필요한 전체 리팩터링 금지.** 이번 변경에 필요한 만큼만 고친다.
- **기존 GAEO 디자인 방향을 임의로 바꾸지 않는다.** 화면 작업 전 `docs/gaeo_design_system.md`를 반드시 읽는다.
- em dash(`—`)를 사용자 노출 텍스트에 쓰지 않는다.
- API 키·secret을 코드에 하드코딩하지 않는다.
- 승인되지 않은 유료 API·외부 서비스를 새로 끌어들이지 않는다.
- main 브랜치에 직접 push하지 않는다(`.analyst-refresh` 마커처럼 명시적으로 허용된 경우 제외). 작업 브랜치에 커밋 → PR → 병합 흐름을 따른다(저장소에 기존에 쓰던 방식과 동일).

## 3단계: 완료 후 안내

구현·자체 테스트까지 마치면 다음처럼 안내한다.

> "개발은 완료됐어요. 배포(커밋·PR·병합) 전에 `/gaeo-review`로 최종 검수를 받는 걸 권장해요."

대표가 바로 배포를 원하면 이 스킬 안에서 커밋·PR·병합까지 진행해도 되지만, 규모가 크거나 위험도가 있는 변경이면 Review를 먼저 거치도록 권한다.

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까 (2026-09-10 절약형으로 개정)

기본은 **메인 작업자 1명**이다. 정상 서버 점검에는 AI를 0명 쓴다(`python3 ops_status.py`·`python3 gaeo_check.py`가 한다).
Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 | 사람 수 |
|---|---|
| 정상 점검·요약·예정 시험 | 0명 (일반 프로그램) |
| 작은 작업(문구·한 줄 수정·단일 화면·소규모 버그) | 메인 1명 + 기계 검사 |
| 보통 작업(기능 구현·다중 파일) | 메인 1명, 독립 판단이 필요한 대목에만 검토자 1명 |
| 보안·장부·투자 성적 의미·배포 경계를 바꾸는 변경 | 메인 1명 + 분리된 검토자 1명(관점별로 **순서대로**, 동시에 여럿 부르지 않는다) |

**동시 실행은 총 2명 이내.** 수정하는 작업자는 언제나 하나이고 검토자는 findings와 근거만 돌려준다(같은 파일을 동시에 고치지 않는다).
자식 Agent의 재귀 생성·끝없는 회의·같은 원본 반복 읽기 금지. 일이 끝난 Agent는 종료한다.
같은 모델의 다른 역할은 완전히 독립된 보증이 아니다 — 기계 검사(`test_*`)를 대체하지 않는다.
역할 파일의 "읽기 전용"은 지침이다(Bash가 있으면 기술적으로 쓸 수 있다). 물리적 차단이라고 말하지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서 (공통 기준 — `docs/HARNESS.md` §3)

`Build` → 기계 검사(`python3 gaeo_check.py quick`/`premerge`) → (중요한 변경만) 독립 검토 → Commit/Push → PR → CI → 병합.
검사·검토에서 FAIL이면 배포하지 않는다. 자동 commit/push 플러그인을 쓰지 않는다.
PR 생성·main 병합은 **그 세션의 사용자 지시 범위 안**에서 확인 없이 진행한다(2026-08-01 고정 승인). 이 순서는 품질 절차이지
추가 승인 단계가 아니다. 단 파괴적·되돌리기 어려운 것(force push·이력 재작성·원장·산식·사전등록 상수 변경·유료 전환)은 항상 명시 승인.
과거 세션의 넓은 승인을 영구 배포 권한으로 쓰지 않는다.
