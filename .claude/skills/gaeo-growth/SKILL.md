# GAEO Growth: 성장을 검토하는 절차

## 언제 쓰나 / 언제 쓰지 않나

| 이 스킬을 쓴다 | 다른 스킬을 쓴다 |
|---|---|
| 유입·재방문·SEO 구조를 검토 | 화면 사용성만 본다 → `/gaeo-design` |
| 새 공개 페이지의 성장 관점 검토 | 개별 글의 SEO 게이트 → 기존 `seo` 계열 스킬 |
| AdSense 배치와 UX 균형 검토 | 전반 점검 → `/gaeo-health` |

⚠️ **광고·수익이라는 단어가 나왔다고 무조건 발동하지 않는다.** 단순한 광고 코드 버그는
`/gaeo-bug`, 광고 영역 레이아웃 깨짐은 `/gaeo-design`이다. 이 스킬은 성장 **전략**을 다룬다.

## 순서 원칙 (절대 뒤집지 않는다)

**좋은 분석 → 사용자 가치 → 재방문 → 트래픽 → 수익화**

광고를 많이 붙이는 방향으로 먼저 가지 않는다. 항상 "사용자에게 도움이 되는가"가 먼저다.

## Agent 구성

- `gaeo-growth-lead`: 유입·SEO·재방문·광고 검토(중심 역할)
- `gaeo-product-lead`: 사용자 가치 관점에서 제안을 걸러줌
- `gaeo-ux-designer`: 광고·성장 시도가 UX를 해치지 않는지 확인
- `gaeo-data-analyst`: 실제 트래픽·전환 데이터가 필요할 때 추가
- 구현 단계로 넘어가면 `gaeo-engineer` 추가

## 검토 항목

- Google 검색 유입, SEO(제목·설명 길이, canonical, sitemap 등. 기술적인 부분은 저장소에 이미 있는 `seo_publish_gate.py`·`docs/gaeo_seo_publishing_rules.md`·`.claude/skills/seo*` 계열을 함께 활용한다. 이 스킬이 그것들을 대체하지 않는다.)
- 종목 페이지·콘텐츠 구조
- 신규 방문자, 재방문, 사용자 유지, 공유
- 페이지뷰, 광고 노출, AdSense, 광고 위치
- 광고가 UX를 훼손하는지 여부

## 절차

1. `gaeo-growth-lead`가 현재 상태를 진단한다(유입 채널, 콘텐츠 구조, 광고 배치 등).
2. 제안마다 `gaeo-ux-designer`가 UX 훼손 여부를 확인한다.
3. `gaeo-product-lead`가 "사용자 가치가 먼저인가, 아니면 단순 트래픽/수익 극대화인가"를 걸러낸다.
4. 실제 수치 근거가 필요하면 `gaeo-data-analyst`가 저장소 내 확인 가능한 데이터로 뒷받침한다(추정만으로 결론 내지 않는다).
5. 구현이 필요한 항목은 `/gaeo-build`로 넘긴다.

## ⭐ 하지 말 것

- 사용자 경험을 해치면서까지 광고·트래픽을 늘리는 제안을 하지 않는다.
- 클릭베이트성 제목, 사실과 다른 콘텐츠를 성장 전략으로 쓰지 않는다.
- em dash(`—`) 등 저장소 콘텐츠 고정 규칙(AGENTS.md)을 어기는 문구를 만들지 않는다.
- 근거 없이 "이러면 트래픽이 는다"고 단정하지 않는다.

## 이 스킬이 자동으로 제안되는 상황

`/gaeo-strategy`, `/gaeo-health`, `/gaeo-build` 도중 아래 조건을 발견하면 사용자에게 이 스킬 실행을 제안한다.

- 새로운 공개 페이지 추가
- SEO 구조 대규모 변경
- 사용자 유입 관련 기능 변경
- AdSense 관련 변경
- 신규 방문·재방문 전략을 오래 점검하지 않은 상태
- 콘텐츠 구조 대규모 변경

제안 문구 예: "최근 공개 종목 페이지 변경 폭이 커서 `/gaeo-growth` 점검을 추천해요."

## ⭐ 공통 운영 규칙 (모든 GAEO Skill 동일)

### Agent를 몇 명 부를까 (2026-09-10 절약형으로 개정)

기본은 **메인 작업자 1명**이다. 정상 서버 점검에는 AI를 0명 쓴다(`python3 ops_status.py`·`python3 gaeo_check.py`가 한다).
Agent가 많다고 결과가 좋아지지 않는다. 같은 파일을 여러 Agent가 반복해서 읽는 것이 가장 큰 낭비다.

| 작업 | 사람 수 |
|---|---|
| 정상 점검·요약·예정 시험 | 0명 (일반 프로그램) |
| 작은 작업(문구·한 줄 수정·단일 화면·소규모 버그) | 메인 1명 + 기계 검사 |
| 보통 작업(기능 구현·다중 파일) | 메인 1명, 독립 판단이 필요한 대목에만 검토자 1명 |
| 보안·장부·투자 성적 의미·배포 경계를 바꾸는 변경 | 메인 1명 + 분리된 검토자 1명(관점별로 **순서대로**, 동시에 여럿 부르지 않는다) |

**동시 실행은 총 2명 이내.** 수정하는 작업자는 언제나 하나이고 검토자는 findings와 근거만 돌려준다(같은 파일을 동시에 고치지 않는다).
자식 Agent의 재귀 생성·끝없는 회의·같은 원본 반복 읽기 금지. 일이 끝난 Agent는 종료한다.
같은 모델의 다른 역할은 완전히 독립된 보증이 아니다 — 기계 검사(`test_*`)를 대체하지 않는다.
역할 파일의 "읽기 전용"은 지침이다(Bash가 있으면 기술적으로 쓸 수 있다). 물리적 차단이라고 말하지 않는다.

부르지 않아도 되는 대표적인 경우:
- CSS 한 줄 변경에 `gaeo-security`를 부르지 않는다
- 일반 코드 수정에 `gaeo-quant-research`/`gaeo-data-analyst`를 부르지 않는다
- 디자인과 무관한 작업에 디자인 보조 스킬(`impeccable` 등)을 부르지 않는다
- 매 작업마다 `skill-creator` 평가를 돌리지 않는다(스킬 자체를 손볼 때만)

### 외부 Plugin·스킬은 GAEO 규칙보다 아래

판단이 충돌할 때의 우선순위는 항상 이 순서다.

1. 사용자(대표)의 명시적 요청
2. GAEO 프로젝트 안전규칙(`AGENTS.md` · `CLAUDE.md`)
3. GAEO Skill 절차
4. GAEO 전문 Agent 판단
5. 외부 Plugin·범용 스킬의 일반 지침

외부 지침 때문에 다음이 일어나는 것을 금지한다: GAEO 디자인 방향이 갑자기 바뀌는 것 ·
승인되지 않은 대규모 리팩터링 · 요청하지 않은 기능 추가 · 자동 commit/push ·
GAEO 워크플로가 외부 방식으로 통째로 대체되는 것.

### 배포 순서 (공통 기준 — `docs/HARNESS.md` §3)

`Build` → 기계 검사(`python3 gaeo_check.py quick`/`premerge`) → (중요한 변경만) 독립 검토 → Commit/Push → PR → CI → 병합.
검사·검토에서 FAIL이면 배포하지 않는다. 자동 commit/push 플러그인을 쓰지 않는다.
PR 생성·main 병합은 **그 세션의 사용자 지시 범위 안**에서 확인 없이 진행한다(2026-08-01 고정 승인). 이 순서는 품질 절차이지
추가 승인 단계가 아니다. 단 파괴적·되돌리기 어려운 것(force push·이력 재작성·원장·산식·사전등록 상수 변경·유료 전환)은 항상 명시 승인.
과거 세션의 넓은 승인을 영구 배포 권한으로 쓰지 않는다.
