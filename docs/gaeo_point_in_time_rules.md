# GAEO Point-in-Time 규칙 (미래정보 차단)

작성일 2026-08-15 · PHASE A · 이후 모든 PHASE가 반드시 지켜야 할 규칙

---

## 1. 원칙

**어떤 판단도 그 판단 시점에 실제로 알 수 없었던 정보를 사용하지 않는다.**

## 2. 현재 구조의 Point-in-Time 상태

### 2-1. 실시간 운영(Live)은 구조적으로 안전하다

현재 파이프라인은 매 사이클마다:

1. 그 시점까지의 시세로 `analysis_data.json` / `indicators.json` 생성
2. 그 시점 데이터로만 `analyze_auto.py` 실행
3. 결과를 `history.js`에 그날 기록으로 append

따라서 `history.js`에 기록된 과거 판단은
**그 당시 실제로 보였던 정보만으로 만들어진 값**이다. 사후 재계산이 아니다.

`base` 93.7%가 그날 종가와 정확히 일치한다는 실측도 이를 뒷받침한다.

### 2-2. **연구용 백테스트에는 심각한 미래정보 위험이 있다 (경고)**

`analyze_auto.py`의 `build_quant_stats()`는
**전 기간 일봉 전체**로 (상태 → 5거래일 뒤 승률) 표를 만든다.

- Live에서는 문제없다. 그 시점까지의 데이터만 존재하기 때문이다.
- **그러나 PHASE C에서 과거를 다시 돌릴 때 이 표를 한 번만 만들어 전 기간에 적용하면
  2026년 7월 판단이 2026년 8월 결과를 이미 알고 있는 상태가 된다.**

이번에 새로 추가된 업종 기저율(`_sectorBase`)도 동일한 위험을 갖는다.

**PHASE C 필수 규칙:**
백테스트 시 각 판단일 T에 대해 `build_quant_stats()`를
**T 이전 데이터만으로 다시 만들어야 한다.** 전 기간 통짜 표 사용 금지.

이 규칙을 어기면 성능이 실제보다 좋게 나온다. 반드시 코드로 강제한다.

## 3. 기록해야 할 Timestamp (현재 미비)

현재 저장되는 것:

- `date` (판단일, 대부분 날짜만. 시각 포함은 16,586건 중 121건뿐)
- `baseAt` (기준가 시점 라벨, 예: "2026-08-14 종가 (16:10 수집)")

**저장되지 않는 것:**

- `workflow_started_at` (실제 워크플로 시작 시각)
- `data_fetched_at`
- `analysis_started_at` / `analysis_completed_at`
- `fundamental_data_available_at`
- `flow_data_timestamp`
- `event_detected_at`

### 절대 금지

**GitHub Actions의 cron 예정시각을 실제 데이터 시각으로 간주하지 않는다.**
예정 10:30, 실제 시작 10:37이면 10:37 이후 유입 데이터는 사용할 수 없다.
현재는 실제 실행 시각이 기록되지 않으므로 사후 재구성이 불가능하다.
PHASE C에서 실제 Timestamp 기록을 추가한다.

## 4. 재무정보 규칙

"2026년 2분기 실적"이라는 이름은
2분기 내내 그 정보를 알았다는 뜻이 아니다.
**실제 공시 시점 이후부터만 사용한다.**

정정보고서로 숫자가 바뀌었다면, 현재 수정값을 과거 시점에 소급 적용하지 않는다.
과거 버전을 재구성할 수 없으면 그 표본의 한계를 기록하거나 보수적으로 제외한다.

## 5. 공시(DART/SEC) 규칙 (PHASE C 구현 예정)

- OpenDART `rcept_dt`는 **YYYYMMDD 접수일자**다. 정확한 시:분:초가 아니다.
- 시각을 임의로 만들어내지 않는다.
- 실시간에서는 GAEO가 처음 발견한 `event_detected_at`을 정확히 기록하고,
  그 시각 이전 판단에는 사용하지 않는다.
- 과거 장중 백테스트에서 정확한 공개시각을 입증할 수 없으면
  **다음 거래일부터 사용**하는 보수적 방식을 쓴다.

## 6. 업종분류 / 유니버스 규칙

- 현재 업종분류를 과거에 그대로 소급하지 않는다.
- 현재 500종목 구성으로 과거 Breadth를 계산하지 않는다.
- 복원 불가능하면 한계를 Validation Report에 명시한다.

현재 상태: `price_history.js`에만 남은 코드 2개(`012510`, `057050`)로
유니버스 변경이 실제 있었음이 확인됐으나, 변경 이력은 저장돼 있지 않다.

## 7. 채점 시점 규칙

채점(`evalRet`)이 미래 종가를 쓰는 것은 정상이다.
채점은 결과 확인이지 예측이 아니다.
**금지되는 것은 "판단 생성"이 미래를 보는 경우다.**
