## 왜 감시 3개가 전부 놓쳤나 — 이게 진짜 원인이다

| ⑤ 매시 Claude Routine | `data.js` **하나만** 쟀다. 시세가 멀쩡하면 자동분석도 멀쩡하다고 암묵적으로 가정했다. |

## 방지책 ⑥ — `pipeline-watchdog.yml`

핵심 원칙 하나로 요약된다:

> **"run이 있는가"가 아니라 "산출물이 갱신되고 있는가"로 판정한다.**

- 판정 근거: `data.js`의 `date` · `auto_analysis.js`의 `generatedAt` 타임스탬프.
  (라벨 파싱은 `check_pipeline.py`의 `read_stamp`를 그대로 import해 쓴다 — 두 감시의 해석이
  갈리면 안 되기 때문이다.)
- **두 파이프라인을 완전히 독립적으로** 판정한다. 한쪽이 멀쩡해도 다른 쪽을 가리지 않는다.
- 평일 장중 **15분 간격**(기존 Routine은 60분 간격이었다).
- 두 러너 워크플로 파일은 **전혀 건드리지 않는다.** AGENTS.md의 "건드리지 말고 이해만 할 것"을
  지키기 위해, 밖에서 감시만 하는 별도 워크플로로 만들었다.

### 건강한 run을 죽이지 않기 위한 유예(grace)

산출물이 낡았다고 무조건 취소하면 **방금 뜬 run이 첫 사이클을 돌기도 전에 죽고 재기동이
무한 반복된다.** 그래서 "이 run이 실제로 일할 수 있었던 시간"을 이렇게 센다:

```
경과 = 지금 − max(run 시작 시각, 오늘 08:58)
```

`max`가 필요한 이유: 러너는 개장 전에 떠서 08:58까지 자도록 **설계돼 있다.** 08:10에 뜬 run을
"1시간 20분째 결과가 없다"고 오해하면 매일 아침 멀쩡한 run을 죽이게 된다.

### 유예를 얼마로 잡을지는 실측으로 정했다

수집창(08:58)이 열린 뒤 그날 **첫** `auto_analysis.js` 커밋까지 걸린 시간 실측:

| 거래일 | 08-25 | 08-26 | 08-27 | 08-28 | 08-31 | 09-01 |
|---|---|---|---|---|---|---|
| 첫 커밋까지 | 14분 | 16분 | 15분 | 17분 | **29분** | 18분 |

처음엔 45분으로 뒀는데 최악값(29분) 대비 **1.55배**밖에 안 된다. **손해가 비대칭이라
넉넉한 쪽으로 옮겼다**: 오판 한 번이면 취소 → 재큐 → 또 취소 루프가 되어 파이프라인이
아예 못 돌지만, 반대로 유예가 길어서 생기는 손해는 hang 감지가 15분 늦어지는 것뿐이고
그건 이번 사고(3시간 20분 방치)에 비하면 무시할 만하다. → **자동분석 60분**(2.07배).

시세는 한 사이클이 ~2분이라 25분이면 12배 이상 여유다.

| 파이프라인 | 첫 커밋 실측 최악 | 유예 | 배수 |
|---|---|---|---|
| update-prices | ~2분 | 25분 | 12배+ |
| update-analysis | 29분 | 60분 | 2.07배 |

### ⚠️ 워치독 자신의 첫 실전 실행에서 드러난 오판 (2026-09-02, 같은 날 수정)

워치독을 배포하고 처음 돌렸더니 **건강한 run을 죽였다.** run 513은 그때 16분째 정상
수집 중이었는데 "136분째 결과가 없다"고 판정했다.

원인은 시각을 잘못 골랐던 것이다. run에는 두 개의 시각이 있다:

| 필드 | run 513의 값 | 뜻 |
|---|---|---|
| `run_started_at` | 09:28 KST | **큐에 들어간** 시각 |
| job의 `started_at` | 11:28 KST | **실제로 러너를 잡은** 시각 |

run 513은 좀비 뒤에서 2시간을 기다렸다가 11:28에야 러너를 잡았다. `run_started_at`으로
재면 그 기다린 2시간까지 "일한 시간"으로 세어 버린다.

**하필 이 워치독이 잡으라고 만든 상황(동시성에 오래 막힘)이 정확히 이 오판을 만든다.**
고치지 않으면 취소 → 재큐(또 오래 대기) → 또 취소가 반복되며 파이프라인을 영원히 못
돌게 만들 수 있었다.

수정: 취소 후보인 `in_progress` run에 한해 `/actions/runs/{id}/jobs`를 한 번 더 조회해
**가장 이른 job의 `started_at`** 을 쓴다. 조회에 실패하면 `run_started_at`으로 물러선다
(그쪽이 더 이른 시각이라 유예를 넉넉히 잡는 방향이므로 안전하다). `Test큐대기_시각_오판`이
이 사고를 재현해 못 박아 뒀다.

교훈: **"언제 시작했나"에도 여러 뜻이 있다.** 기다린 시간을 일한 시간으로 세면 안 된다.

### 대기 중인 run의 이름이 하나가 아니다

GitHub는 "아직 시작 못 한 run"을 한 이름으로 부르지 않는다. **동시성에 막혀 대기 중인 run은
`pending`** 으로 뜨고(2026-09-02의 run 513이 실제로 그랬다), 러너를 기다리는 run은 `queued`다.
하나만 조회하면 "좀비 뒤에 대기분이 있는지"를 놓쳐서, 좀비를 치운 뒤 필요 없는 dispatch를
한 번 더 쏘게 된다. 그래서 `queued` · `pending` · `waiting` · `requested`를 모두 대기로 센다.

| 파이프라인 | 주기 | 산출물이 낡았다고 보는 임계 | 좀비 판정 유예 |
|---|---|---|---|
| update-prices | 10분 | 25분 | 25분 |
| update-analysis | 30분 | 70분 | 60분 |

### v2가 시작할 때 워치독을 직접 깨우는 이유 — GitHub cron은 믿을 수 없다

⑥ 워치독은 GitHub cron으로 15분마다 돌게 돼 있지만, **이 저장소에서 GitHub 무료 cron은
잘 밀리거나 빠진다**(러너 두 개가 자기 재기동 체인을 쓰는 이유가 바로 이것이다). 실제로
워치독을 신설한 직후 12:00·12:15 KST 예정분이 돌지 않았고, 워크플로 상태는 `active`였다 —
설정 문제가 아니라 cron 지연이다.

그래서 v2 Routine(Claude 스케줄러 — 매시 확실히 온다)이 **0단계로 워치독을 `workflow_dispatch`로
한 번 깨운다.** cron이 어떻든 매시 최소 1회는 테스트된 결정론 판정이 돈다. Routine 자체의
점검(Claude가 직접 판단)은 그 워치독까지 멈춘 경우의 뒷단이다. 중복 조치를 막기 위해, Routine은
자체 조치 전에 방금 깨운 워치독 run의 로그를 먼저 확인한다.

v2 프롬프트 전문은 아래에 그대로 남겨 둔다 — 나중에 Routine을 다시 만들거나 손볼 때 이 문서가
원본(Source of Truth)이다. ⑥번 워치독이 15분 간격으로 같은 일을 먼저 하므로, v2는 그 워치독까지
멈춘 경우를 대비한 뒷단이다.

```
⚠️ 가장 중요한 규칙 — 2026-09-02 사고의 교훈: 예전 이 Routine은 data.js(시세) 하나만 보고 "정상"이라 판단했다. 그날 시세는 10분마다 멀쩡히 갱신되는데 자동분석만 전날 16:08에 얼어붙어 있었고, 이 Routine은 매시간 조용히 종료했다. 화면엔 아침 내내 "분석 기준 어제 · 재분석 권장"이 떴다. 시세가 멀쩡한 것은 자동분석이 멀쩡하다는 근거가 전혀 아니다. 반드시 둘을 따로 재라.

1. `git fetch origin main`으로 최신을 받는다. 두 산출물의 신선도를 각각 계산한다:
   - 시세: `git show origin/main:data.js | head -5`의 "date" 라벨 시각 → 지금과의 간격. 임계 25분.

   (참고: 로컬을 origin/main에 맞춘 뒤 `python3 pipeline_watchdog.py`를 돌리면 이 두 값을 그대로 계산해 준다. 토큰 없이 돌리면 판정만 하고 조치는 안 한다.)
2. 둘 다 임계 미만이면 정상이니 조용히 종료한다(보고 생략). 0단계에서 워치독을 깨운 것도 보고하지 않는다.
3. 어느 한쪽이라도 임계를 넘겼으면, 넘긴 쪽 워크플로만 대상으로 아래를 수행한다. 시세가 멀쩡하면 update-prices는 건드리지 말고, 자동분석만 멈췄으면 update-analysis만 처리한다. 단, 0단계의 워치독이 이미 조치했을 수 있으니 먼저 pipeline-watchdog.yml의 방금 run 로그(mcp__github__get_job_logs)를 확인하고, 거기서 이미 취소·재기동이 됐으면 중복 조치하지 말고 5번으로 간다.
   - 그 워크플로의 최근 run 상태를 GitHub Actions에서 확인한다(mcp__github__actions_list → list_workflow_runs, 그리고 list_workflow_jobs로 job의 started_at도 본다).
   - in_progress인 run이 있는데도 산출물이 임계를 넘게 갱신 안 됐다면 그 run은 좀비(hang)다. cancel-in-progress: false라 새 트리거가 밀어내지 못하고 pending으로 대기만 한다(AGENTS.md 데이터 파이프라인 절). ⚠️ "run이 in_progress다 = 살아있다"로 판단하지 마라 — 그게 정확히 이 사고를 2시간 놓친 이유다. 판단 기준은 오직 산출물이 갱신되고 있는지다.
   - 같은 워크플로에 pending/queued run이 함께 있으면 그건 좀비 뒤에 줄 서 있다는 확실한 신호다. 좀비를 취소하면 그 대기분이 자동으로 시작되므로, 이 경우 별도 kickoff은 필요 없다.
   - ⚠️ 유예: 러너를 실제로 잡은 시각(job의 started_at, run의 run_started_at이 아님 — 그건 큐에 들어간 시각이다)부터 60분 안이면 아직 첫 사이클을 못 끝냈을 수 있으니 취소하지 마라. 개장 전(08:58 이전)에 뜬 run은 08:58까지 자도록 설계돼 있으니 "돈 시간"은 max(러너 잡은 시각, 오늘 08:58)부터 세라. (실측: 수집창이 열린 뒤 첫 자동분석 커밋까지 14~29분.)
   - 조치: mcp__github__actions_run_trigger의 cancel_workflow_run으로 좀비 run을 취소한다. 그 뒤 대기 중인 run이 하나도 없을 때만 4번 kickoff을 한다.
   - 실행 중인 run이 아예 없으면(완전히 죽은 상태) 바로 4번 kickoff.
4. kickoff: `.analyst-refresh` 파일에 현재 시각(KST)과 무엇을 되살리는지를 한 줄 추가하고 main에 직접 커밋·푸시한다(이 파일 경로 push가 두 워크플로우의 공통 트리거 조건). 별도 브랜치·PR 불필요.
5. 5~10분 후(가능하면 Actions API로) 새 run이 시작됐는지 한 번만 가볍게 확인한다. 여러 번 폴링하거나 sleep으로 대기하지 않는다.
6. 결과가 "둘 다 정상"이면 아무 것도 보고하지 않는다. 실제로 취소·kickoff을 했을 때(워치독이 한 것을 확인한 경우 포함)만 사용자에게 한두 문장으로 짧게 보고한다 — 어느 쪽(시세/자동분석)이 몇 분째 멈춰 있었는지를 반드시 포함할 것. 보고는 CLAUDE.md 규칙대로 초등학생도 알아듣는 쉬운 말로.

주의: 이 Routine은 안전망일 뿐이다 — analysis.js의 개별 종목 정밀분석이나 다른 콘텐츠 파일은 절대 건드리지 않는다. `.analyst-refresh` 외 다른 파일을 수정하지 않는다.
```

## 앞으로 감시를 만들 때의 규칙

**"run이 돌고 있다"를 건강 신호로 쓰지 마라.** 산출물이 갱신되는지를 봐라.
그리고 파이프라인이 여러 개면 **각각 따로** 재라 — 하나가 멀쩡한 게 다른 하나의 근거가 될 수 없다.
