## 수정 1. HOLD 채점 규칙 3원화 → 1원화 (엄격)

### 문제

같은 저장소 안에 HOLD 채점 규칙이 **3가지**로 갈라져 있었다.

| 위치 | HOLD가 ±5%를 벗어나면 | 성격 |
|---|---|---|
| `index.html` `scoreCall()` | `mid`(중립) | 관대 |
| `compute_team_weights.py` `score_call()` | `mid`(중립) | 관대 |
| `compute_model_intelligence.py` `call_hit()` | `0`(빗나감) | 엄격 |

결과: **같은 데이터로 통산 적중률이 70.7%(관대) vs 51.2%(엄격)로 19.5%p 갈렸다.**

게다가 성적표 화면 안에서도 모순이 있었다.
헤드라인 지표는 `scoreCall`(관대)로, 바로 아래 "판단 종류별 성적" 표는
`scTally(holdStrict=true)`(엄격)로 계산돼 서로 다른 숫자를 보여주고 있었다.

### 수정

**엄격 쪽으로 통일했다.** HOLD는 "크게 안 움직인다"는 예측이므로
크게 움직였으면 빗나간 것이 맞다.

- `index.html scoreCall()`: `'mid'` → `'miss'`
- `compute_team_weights.py score_call()`: `"mid"` → `"miss"`
- `compute_model_intelligence.py call_hit()`: 이미 엄격, 변경 없음
- `VERDICT_TIP` 툴팁 문구도 HOLD 빗나감 경우를 포함하도록 수정

### 수정 전/후

**팀 통산 성적 (`team_weights.js`)**

| | 적중 | 빗나감 | 표본 | 적중률 |
|---|---|---|---|---|
| 수정 전 | 6,918 | 2,871 | 9,789 | **70.7%** |
| 수정 후 | 6,918 | 6,583 | 13,501 | **51.2%** |

**분석가 가중치 (모델 동작 확인용)**

| | TARO | DIANA | QUANT | FLOW |
|---|---|---|---|---|
| 수정 전 | 0.2831 | 0.1159 | 0.2921 | 0.3089 |
| 수정 후 | 0.2831 | 0.1159 | 0.2921 | 0.3089 |

**완전히 동일하다.** `score_call`은 표시용 team 요약에만 쓰이고
가중치는 `score_stance`에서 나오므로 모델 동작은 바뀌지 않았다.

**주간 성적표 헤드라인 (2026-08-09 ~ 08-15)**

| | 적중 | 빗나감 | 중립 |
|---|---|---|---|
| 수정 전 | 826 | 959 | 715 |
| 수정 후 | 826 | **1,587** | **87** |

수정 후 헤드라인과 판단 종류별 표가 정확히 맞아떨어진다:

- HOLD 1,302 = 674 적중 + 628 빗나감 (51.8%)
- BUY 114 = 60 적중 + 40 빗나감 + 14 중립 (60%)
- SELL 1,084 = 92 적중 + 919 빗나감 + 73 중립 (9.1%)
- 합계 826 / 1,587 / 87 ✔

## 수정 2. `evalClose()` 정렬 누락 (잠재 버그)

### 문제

`flatCloses()`는 "PRICE_HISTORY의 페이지 배열은 시간순이 아닐 수 있다"는
경고 주석을 달고 정렬한다(AGENTS.md 주의 2번과 동일). 그런데 채점 함수
`evalClose()`는 `flatMap` 후 정렬하지 않았다.

### 재현 (합성 데이터)

판단일 2026-01-05, 이후 거래일 01-06/07/08/09/12/13/14/15/16.
정답은 5번째 거래일 = **2026-01-12 (종가 105)**.

| 페이지 상태 | 수정 전 | 수정 후 |
|---|---|---|
| 정상 순서 | 01-12 (105) OK | 01-12 (105) OK |
| 순서 뒤바뀜 | **01-16 (109) 오답** | 01-12 (105) OK |

같은 판단의 수익률이 페이지 순서에 따라 **+5.0% vs +9.0%**로 달라졌다.
실제 버그가 맞다.

### 수정

`.sort((a,b)=>a.date<b.date?-1:(a.date>b.date?1:0))` 추가.

### 회귀 영향

현재 실데이터 502종목 전부 페이지 순서가 정상이라 **발현되지 않던 상태**였다.
수정 전/후 채점 결과 대조: **14,063건 전부 동일, 차이 0건.**

즉 이 수정은 지금 숫자를 바꾸지 않으면서 미래 사고만 막는다.

## 수정 4. 실제 실행시각 기록 구조

### 문제

cron 예정시각과 실제 실행시각이 다를 수 있는데, 실제 시각이 저장되지 않아
"이 판단이 실제로 무엇을 보고 내려졌는지" 사후 재구성이 불가능했다.

### 수정

`auto_analysis.js`에 `runTimestamps` 블록을 추가했다.

```json
"runTimestamps": {
  "workflowStartedAt": "2026-08-15T01:07:33Z",   // 러너 실제 사이클 시작
  "priceFetchedAt":    "2026-08-15T01:19:02Z",   // 시세 실제 수신
  "analysisStartedAt": "2026-08-15T10:20:11+09:00",
  "analysisCompletedAt":"2026-08-15T10:32:44+09:00",
  "priceLabel": "2026-08-14 종가 (16:10 수집)",
  "cronScheduledNominal": "*/30 0-7 * * 1-5",    // ⚠️ 예정값. 데이터 시각으로 쓰지 말 것
  "githubRunId": "...", "githubRunAttempt": "..."
}
```

- 워크플로가 사이클 시작 시 `GAEO_CYCLE_STARTED_AT`,
  시세 재동기화 직후 `GAEO_PRICE_FETCHED_AT`를 실제 UTC 시각으로 주입
- `analyze_auto.py`가 자신의 시작·완료 시각을 직접 기록
- **환경변수가 없으면 `null`.** 시각을 지어내지 않는다.
  로컬 실행에서도 파이프라인이 죽지 않는다(단위 테스트로 확인).
- 예정값(`cronScheduledNominal`)은 실제 시각과 **분리해서** 저장하고
  데이터 시각으로 쓰지 말라고 `note`에 명시했다.
